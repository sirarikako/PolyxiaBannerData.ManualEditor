# Codex + DeepSeek Harness 自动协作流程

本流程服务于后续 Flutter Windows + Android 开发，使用 Codex 自身的命令执行能力调用 DSH。硬性规则见 [AGENTS.md](../AGENTS.md)，Review 时使用 [检查清单](agent-review-checklist.md)，本地与云端分工及工作流契约见 [CI、构建与发布](ci-build-release.md)。

主流程：需求 → Codex 设计 → DSH 开发 → Codex 本地 Review → 必要返工 → Feature Branch / PR → GitHub CI → Codex 分析 CI → 必要时 DSH 修复 → CI 复验 → 用户验收。独立分支在开发前建立，PR 阶段仅在获得远端操作授权后推进。

## 1. 已知基础与验证边界

用户已完成的实验表明：Codex 可以通过 `dsh --profile headless` 调用 DSH、读取退出码与输出、独立 Review 和故障注入、再调用 DSH 返工。该实验共调用 DSH 2 次，返工 1 轮，22 个交付测试和 55 个独立验收场景通过。

上述数字是用户提供的历史实验结果，不是本次文档任务的执行结果。本次不重复实验，不执行新的业务开发。命令入口可复用，但完整任务输入方式、具体 CLI 参数、版本及超时处理细节，应以已保存的成功命令或后续任务开始时读取的本机帮助为准，不在文档中虚构。

## 2. 分工和任务记录

Codex 决定做什么、允许改哪里、如何验收，以及结果能否交付。DSH 编写主要业务实现和相关开发测试，执行测试并修复问题。Codex 可以维护文档、设计独立验收和测试夹具，但不得自己重写业务实现来消除 Review 问题。

每个任务保留一份简明任务记录，可直接放在当前会话中。无需增加任务数据库、后台服务或专用文件。至少记录：

- 目标、范围、禁止事项、平台与验收条件。
- 当前目录、任务分支、起始 Git 状态、起始提交（如有）、原有修改基线。
- DSH 调用总数、返工轮数及本地 / CI 触发来源、每次调用的阶段、执行时限和脱敏结果。
- 每轮修改证据、Review 问题、实际验证命令和结果。
- 代码验收、云端构建、Windows / Android 实机验收的分别状态；有云端执行时记录提交 SHA、Run 链接及产物。
- 阻塞、未验证项目、最终状态及需要用户决定的事项。

单个任务初次开发 1 次，最多自动返工 3 轮，总调用尝试最多 4 次；本地 Review 返工和 CI 返工共用这一预算，不各自获得 3 轮。该计数针对开发和返工的 Headless 执行尝试，只读帮助或版本查询作为环境检查另行记录，不占返工轮数。任务分解不重置预算，不能靠重新命名或开启新会话绕过上限。DSH 启动失败、调用失败、超时和授权阻塞均计入调用次数，且立即触发停止，不以剩余预算为由重试。

## 3. 阶段 A：分析、基线和任务边界

1. 阅读用户需求、适用的 `AGENTS.md`、现有协作文档和与任务相关的源码、测试及配置。
2. 用 PowerShell 和 Git 检查工作目录、分支、工作区、暂存区和未跟踪文件。例如：

   ```powershell
   Get-Location
   git branch --show-current
   git status --short
   git diff --stat
   git diff
   git diff --cached
   git ls-files --others --exclude-standard
   ```

3. 记录已有修改。不得覆盖、回退、暂存或提交用户已有内容；也不得自动 `stash`。如果与本任务有冲突且无法安全隔离，停止并说明冲突文件。
4. 创建独立的 `codex/<任务名>` 分支，或复用明确属于本任务的独立分支。未经用户明确授权不在 `main` 上修改文件。不要为了分支切换强制丢弃修改。
5. 将需求拆成有限、可验证的工作项。为每项定义允许修改的目录或文件、禁止事项、行为验收条件、适用平台及相关测试；明确哪些属于本地代码验收、云端构建、实机验收及用户验收。拆分不授权扩大范围。
6. 记录已安装工具与测试条件，核对本地 Flutter 版本与 `.fvmrc`。Hyper-V VM 负责快速测试，完整构建优先使用云端；缺少 Android Studio、NDK 或模拟器不构成自行安装理由。Android 优先使用真机 Wi-Fi ADB，必要时使用宿主机 Emulator。缺失项阻塞必需验收时，报告阻塞，不宣告通过。

对于尚无提交的仓库，`HEAD` 和提交间 Diff 不可用，应明确记录“无初始提交”。用文件内容基线及新文件全文审查代替，不能为制造基线擅自提交。普通 `git diff` 不显示未跟踪新文件，必须另行检查全文或使用只读的 `git diff --no-index` 与空文件比较。

## 4. 阶段 B：向 DSH 下达开发任务

使用下列任务单组织提示词；实际内容由 Codex 根据仓库分析填写。不要把凭据放进任务单。

```text
任务目标：
仓库工作目录与任务分支：
已存在的用户修改及保护要求：
允许修改的目录或文件：
禁止修改的目录或文件：
工作项与行为要求：
验收条件（含边界、异常、回归与平台要求）：
本地快速测试或检查命令：
云端构建及实机验证要求（由 Codex 协调，不要求 DSH 在 VM 补齐大型 SDK）：
执行时限：

你是主要开发执行者。请编写实现和必要测试，运行相关测试并修复发现的问题。
遵守本仓库 AGENTS.md，不扩大范围、不降低验收标准、不删除或禁用有效测试。
不提交、不切分支、不推送、不创建或合并 PR，不安装软件，不修改永久环境配置。
发现需要人工授权、认证问题、无法解决的阻塞或范围外依赖时，停止并报告。
完成后列出修改文件、实现说明、实际测试命令及结果、遗留问题和未验证平台。
```

调用约束：

- 使用已验证的 `dsh --profile headless` 入口，在任务仓库目录执行；任务输入方式及其他参数来自现有成功命令或本机帮助，不能猜测 `--prompt`、`--cwd` 等参数存在。
- 调用前记录明确的执行时限。会话等待时限和进程总执行时限应区分；必须能够继续读取同一个进程的输出与最终退出码。
- 命令工具返回进程仍在运行时，继续跟踪该会话，不重复启动 DSH，不提前审查仍在变动的文件或启动返工。
- 达到总时限后，只尝试终止本次明确归属的 DSH 进程及其子进程，不批量终止其他会话。无论是否确认终止，都停止自动流程；未确认结束时明确标注，不启动并发写入。
- 不打印完整环境或认证配置。发现已有变量干扰认证时，只在 DSH 子进程环境副本中临时移除已确认冲突的变量，保留父会话及永久配置；不能安全做到时停止并报告。
- 调用启动失败、非零退出、超时或要求人工授权时，记录脱敏错误和已有改动，停止并报告，不自动重试。

## 5. 阶段 C：Codex 独立 Review 和验收

DSH 正常结束后，Codex 依次检查以下证据，不能仅依据 DSH 总结判定通过：

1. **执行结果**：读取最终退出码和实际输出，核对 DSH 声明的文件、测试及问题。退出码为 0 只表示进程正常结束。
2. **实际差异**：核对当前分支和 `HEAD`，检查工作区、暂存区、未跟踪文件及删除文件；同时审查本轮相对基线的变化和任务累计变化。有起始提交时，还要检查从起始提交到当前状态的实际差异，防止已提交修改被漏审。DSH 意外提交或切分支时停止并保留现场，不自动回滚。核对改动范围，检查忽略规则、配置、锁文件及生成物是否掩盖额外修改。
3. **实现质量**：结合上下文阅读代码，检查需求覆盖、边界、异常、数据完整性、回归风险和平台差异；具体项目见检查清单。
4. **独立验证**：Codex 自行执行相关自动化测试并读取真实输出，针对关键行为补充最有价值的独立验收；高风险行为必要时做故障注入。DSH 的测试报告可提供线索，不能替代独立执行证据。
5. **本地通过条件**：代码范围内必需验收项满足，相关本地自动化检查通过，范围合规，且无未解决的代码阻断问题，才记录“本地 Review 通过”并进入 CI 阶段。需要 CI 的任务，最终“代码验收通过”还须结合该提交的 CI 检查；云端构建和设备结果另行记录，不能由本地结果宣告任务完整通过。

测试按变更选择，不把下表中的命令当作每次任务的固定全集；具体命令与参数以仓库配置为准。

| 修改类型 | 基本验证 | 风险驱动的补充验证 |
| --- | --- | --- |
| 文档、规则 | 链接目标、规则一致性、文件范围、完整 Diff、空白错误 | 核对示例和实际环境；不做业务开发实验 |
| Dart 逻辑、模型或状态 | 格式、相关静态检查、单元测试，如 `flutter analyze`、`flutter test` | 空值、空集合、边界数值、异常与回归案例 |
| Flutter UI 与交互 | 相关组件测试、静态检查 | 状态切换、尺寸变化、输入和错误展示、关键集成路径 |
| Windows 特有功能 | 本地可执行的平台测试，按需申请云端 Windows 构建 | 文件路径、文件锁、权限失败、窗口行为；目标 Windows 环境实机验收 |
| Android 特有功能 | 本地可执行的测试，按需申请云端 APK 构建 | 真机 Wi-Fi ADB 验证权限、生命周期、存储或插件行为；宿主机模拟器可作补充 |
| 文件读写、持久化或外部交互 | 正常与失败路径的自动化测试 | 临时数据上的损坏输入、写入失败、中断恢复；不触碰真实数据 |

故障注入必须在临时数据、临时目录或可控测试夹具上执行，并在结束后检查和清理本次测试副作用。不能通过删除测试、弱化断言、跳过失败项、硬编码测试结果或绕过校验获得通过。测试本身确有错误时，修正必须说明依据、保留原有行为保障并由 Codex 审查；需求变化导致验收条件变化则先由用户确认。

Windows 与 Android 的平台特有行为分别记录。Android 构建、模拟器验证和实机验证是不同证据；没有实机条件时写明“Android 实机测试未执行”，只报告实际完成的验证。若该项属于必需验收，任务不能标记完整验收通过。

## 6. 阶段 D：自动返工与复验

正常完成的 DSH 调用经本地 Review 或 CI 分析发现实现或测试不满足验收时，由 Codex 发起返工；DSH 调用故障不进入自动返工，CI 基础设施故障则先报告阻塞。

1. 先记录本轮 Git 状态、文件内容或相对于任务基线的差异，以便判断下一轮实际改动。可使用命令输出和临时快照，不要求增加脚本或在仓库中生成记录文件，也不要为留证据自动提交。
2. 明确指出问题所在的文件或行为、复现步骤、观察结果、期望结果、影响和验收方法。不能只说“继续修复”或“让测试通过”。
3. 在原范围内要求 DSH 修复，并执行问题相关测试和必要回归测试。先增加调用次数及共享返工轮数，记录触发来源，再启动调用。一次 DSH 返工同时处理多个 CI Job 的问题仍算 1 轮；分别调用则分别计数。
4. DSH 返回后重新执行阶段 C：检查该轮实际差异、任务累计差异、问题专项验证及相关回归；不能只检查文字报告或只重跑 DSH 新增的测试。CI 问题修复后还需按阶段 E 验证新提交对应的 CI。
5. 如仍未通过且返工不足 3 轮，给出新的明确问题单；第 3 轮仍未通过则停止，不发起第 4 轮。

返工任务单：

```text
原任务与当前分支：
返工轮次：第 N / 3 轮
触发来源：本地 Review / CI（共用预算）
本任务已发起 DSH 调用次数：
本轮执行时限：
继续遵守的范围与禁止事项：

问题编号与位置：
证据或复现步骤：
实际结果 / 期望结果：
影响：
允许的修复边界：
验收条件及专项测试：
需要复跑的回归测试：

请修复以上问题，报告实际修改和测试结果；不得降低验收标准或扩大范围。
```

如果问题无法在现有范围、环境或授权内解决，即使返工预算未耗尽，也应停止并报告。Codex 不以接手业务重写、放宽标准或重新拆单来绕过停止条件。

## 7. 阶段 E：PR、GitHub CI 与用户验收

1. 本地 Review 通过后，Codex 仅按当前授权提交、推送 Feature Branch 并创建或更新 PR；没有远端写入授权时停在可审查的本地结果，报告 CI 尚未执行。不得自动合并 PR。
2. GitHub Actions 仅执行检查、构建和已授权的发布，不运行 Codex、DSH 或其他 AI Agent。三个计划工作流的触发、权限及产物要求统一见 CI、构建与发布文档；普通 PR 不默认执行完整双平台构建。
3. Codex 在本地读取实际 CI Run、Job、失败步骤、退出信息和必要日志，记录 PR head SHA 与实际受测 SHA（PR 可能测试合并提交）。旧提交的绿灯不能替代新提交的验证。
4. CI 失败时先区分代码、测试、配置问题与 Runner、网络、权限等基础设施问题。前者在原授权范围及剩余预算内交给 DSH 修复；后者停止并报告，不通过猜测改代码或反复重跑掩盖问题。修复涉及范围外文件时先报告边界冲突。
5. CI 返工回到阶段 D，并共用最多 3 轮预算。例如本地已返工 2 轮，CI 最多再返工 1 轮；本地已用满 3 轮后发现 CI 问题，应停止报告。只读分析日志或无代码变化的 CI 重跑不计作 DSH 返工，但不得借此无限重试，基础设施故障按停止规则处理。
6. 修复经本地复验后，由 Codex 按既有授权推送新提交，检查该提交对应的新 CI；按任务需要触发指定平台云端构建，核对真实成功状态与可用产物。手动构建成功不绕过失败的必需 CI。
7. 对匹配提交和产物进行 Windows / Android 设备验收，分别记录设备类型、版本、执行结果和未执行项。宿主机 Android Emulator 的结果标为模拟器结果，不能计为 Android 实机通过。最后交由用户验收；等待用户验收时如实记录，不代替用户确认。

## 8. 停止状态与交付报告

| 情况 | 后续动作 |
| --- | --- |
| 当前阶段通过，后续构建、设备或用户验收待执行 | 仅报告该阶段通过，继续授权范围内的流程或列明待办 |
| 全部必需验收通过且用户验收要求已满足 | 报告完成；仅执行当前任务授权的后续动作 |
| 本地 Review 或 CI 发现问题且共享预算允许 | 进入明确问题驱动的返工 |
| DSH 调用失败、超时、人工授权、无法确认进程结束，或 CI 基础设施故障 | 停止自动流程，保留改动和脱敏证据，向用户报告 |
| 无法解决、范围冲突、必需条件缺失或返工耗尽 | 停止并报告阻塞或未完成；等待用户新的处理指令 |

每次任务结束都使用下列报告要素，包括停止和纯文档任务：

```text
完成状态：已完成 / 部分完成（未完整验收）/ 已停止（原因）
DSH 调用总次数：N；自动返工轮数：M / 3（本地 L 轮 + CI C 轮）
修改文件：路径及主要变更
Git Diff 审查：分支、实际范围、主要发现及是否解决
验证：实际执行的命令或检查、结果及必要的证据
代码验收：通过 / 不通过 / 未执行 / 不适用
云端构建：Android 与 Windows 分别记录；提交 SHA、Run 和产物链接
Windows 实机验收：状态、设备和产物版本
Android 实机验收：状态、设备和产物版本；模拟器结果单列
用户验收：已确认 / 待确认 / 不适用
未解决问题与未验证环节：包括 Windows / Android 分别的状态
是否需要用户确认：否 / 是（具体决策及原因）
```

没有调用 DSH 时记录 0 次、0 轮；没有运行业务测试时说明原因，不套用历史实验数字。不得把未提交、未推送或未创建 PR 自动描述成工作未完成，这些操作取决于本次任务授权。

## 9. 最小实现与首个 Flutter 任务

当前流程使用 Codex 的命令执行、会话跟踪、文件读取和 Git 检查能力即可，不增加 Python、Node.js 或 PowerShell 调度程序，不引入数据库、后台服务、消息队列或第三方依赖。调用时的普通 PowerShell 命令不构成需要长期维护的新调度平台。

只有真实任务暴露出现有能力无法安全处理的具体问题时，才讨论最小辅助配置或脚本；先说明问题、范围与维护成本，遵循用户授权，不预先搭平台。

首个真实开发任务按以下顺序开始：

1. 用户给出一个边界明确的 Flutter 需求、实际项目位置、Windows / Android 目标和可用设备；缺少信息时，Codex 先分析已有仓库，只询问影响实施或验收的关键缺项。
2. Codex 检查项目和工具现状、Git 基线，建立任务分支，拟定范围、分层验收标准和本地 / 云端测试计划；核对 `.fvmrc` 及已有 CI 配置是否存在。空仓库需要先明确是创建新 Flutter 项目还是使用现有项目，不能假设已有业务代码或云端工作流。
